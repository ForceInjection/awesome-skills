# Format Review Rules (Typography Proofreader)

The core of this review type is **purely visual typography and Markdown syntax conventions**.
**Execution strategy**: After the content is finalized, quickly scan the entire document. Focus on fine-grained formatting issues such as Chinese-English typography, punctuation, and indentation alignment. For issues found in this review type, the Agent is **strongly advised to provide one-click silent auto-fixes**.

- **Document Navigation (TOC)**: For long documents (e.g., those containing multiple second/third-level headings), check that the beginning includes a `TOC (Table of Contents)` to enhance navigation friendliness.
- **Heading Language**: Use only one language in headings — **no bilingual headings**.
  - Correct: `## 核心架构设计`
  - Incorrect: `## 核心架构设计 (Core Architecture Design)`
- **Section Numbering**: The document must use sequential numbering (e.g., `1.`, `1.1`, `1.1.1`). **Note the placement of numbers**: numbers must be written inside the heading text, not applied to the Markdown hash marks (`#`, `##`, `###`). The top-level document title (`# Document Title`) needs no number.
  - Correct: `## 1. 核心概念`
  - Incorrect: `## 1. 1. 核心概念` (duplicate numbering)
  - Incorrect: `## 核心概念` (missing the required section number)
- **Chinese-English Spacing**: A space is required between Chinese and English text.
  - Correct: `使用 Python 编写`, `基于 RDMA 的传输`
  - Incorrect: `使用Python编写`, `基于RDMA的传输`
- **Chinese-Number Spacing**: A space is also required between Chinese text and numbers.
  - Correct: `延迟低于 50 μs`
  - Incorrect: `延迟低于50μs`
- **Punctuation**: Chinese documents primarily use full-width punctuation (，。：；？！), but use half-width punctuation around numbers, English words, and code snippets.
  - Correct: `支持 vLLM、TGI 等框架。`
  - Incorrect: `支持vLLM,TGI等框架.`
- **Proprietary Names**: Strictly follow official capitalization.
  - Correct: `vLLM`, `Redis`, `MySQL`, `iOS`
  - Incorrect: `vllm`, `redis`, `mysql`, `ios`
- **Table Format**: Do **not** use HTML tags such as `<br>` in Markdown tables. Table content must be aligned with reasonable column widths. For comparison tables: when comparing multiple options or features, present them clearly in a Markdown table.
- **List Format**: Use bold keyword + colon format for definition lists. List items that are complete sentences end with punctuation; phrases may omit it.
  - Correct: `- **L1 极速内存层**：GPU 显存，保存活跃数据。`
- **Alerts/Callouts**: Prefer standard GitHub-style extended syntax (e.g., `> [!NOTE]`, `> [!WARNING]`, `> [!TIP]`); avoid bold-only or non-standard custom prefixes.
  - Correct:

    ```markdown
    > [!WARNING]
    > Do not use the default password in production.
    ```

  - Incorrect: `**Warning**: Do not use the default password in production.`

- **Avoid Formatting Abuse**: Check for overuse of bold, italics, or highlighting (e.g., consecutive lines fully bolded). Emphasis should stay focused to avoid harming the overall reading experience.
- **Section Separation**: Separate major top-level sections with `---` horizontal rules.
- **Code Block Format**: Code blocks must specify their language type (e.g., ` ```python `).
- **Visual Elements**:
  - **Mermaid Diagrams**: Prefer Mermaid for architecture diagrams and flowcharts; avoid non-editable images generated by external tools.
  - **ASCII Diagrams**: For simple schematics, ASCII diagrams can quickly convey the idea, e.g.:

    ```text
    +--------+     +--------+     +--------+
    | Client | --> | Server | --> |  DB    |
    +--------+     +--------+     +--------+
    ```

  - **LaTeX Formulas**:
    - **Basic Syntax**: Use `$...$` (inline) or `$$...$$` (block) LaTeX syntax for math formulas.
    - **Spacing Around Formulas**: Inline formulas `$...$` must have spaces between them and surrounding text to ensure correct rendering on GitHub and other platforms. **Correct example**: `Length: $P$ tokens`; **Incorrect example**: `Length:$P$ tokens`.
    - **Text and Subscripts**: Use `\text{...}` for descriptive text or multi-character subscripts in formulas (e.g., `\text{Memory}_{KV}`).
    - **Code Variables**: Wrap code variable names in `\texttt{...}` to keep the monospace style (e.g., `\texttt{block\_size}`).
    - **Operators and Symbols**: Use `\times` instead of `*` for multiplication; use `\approx` for approximate equality; use `{,}` for thousands separators (e.g., `57{,}344`).
    - **Units**: Separate values and units with `\,`; set units upright with `\text{...}` (e.g., `1.12\,\text{GiB}`).
